1. LINUX SECURITY
FOUNDATIONS

LINUX SECURITY LAYERS

Linux security is built in multiple layers including the kernel, system services, filesystem, users, and network. Every component interacts — securing each layer reduces risk across the entire system.

AUTHENTICATION VS AUTHORIZATION

Authentication verifies who you are. Authorization determines what you are allowed to do. Both must be configured correctly for the system to remain secure.

LEAST PRIVILEGE

Users, services, and processes should have only the minimum permissions required to perform their tasks. Limit access to reduce risk.

ATTACK SURFACE

Any point that can be used to attack your system. Reduce exposed services, open ports, and unnecessary access to shrink the attack surface.

DEFENSE IN DEPTH

No single control is perfect. Use multiple layers of security so that if one layer fails, other layers continue to protect the system.

SECURITY BASELINE VS ONGOING MONITORING

A strong baseline sets the foundation. Continuous monitoring detects changes, threats, and abnormal behavior early.

KEY PRINCIPLES

Kernel, services, filesystem, users, and network are all security layers.

Authentication answers who you are; authorization answers what you can do.

Grant only the minimum permissions required for each task.

Reduce exposed services and open ports to shrink the attack surface.

Combine multiple controls so a failure in one layer does not compromise the system.

Set a strong baseline, then monitor continuously for change.

whoami Show the current effective user
id Show UID, GID, and group memberships

LOCKING AND DISABLING ACCOUNTS

REVIEWING PRIVILEGED USERS

3. PASSWORD AND
ACCOUNT SECURITY

PASSWORD AGING

Defines the minimum number of days before a password can be changed again. Prevents frequent and weak password changes.

PASSWORD EXPIRATION

Forces users to change passwords after a specified number of days. Reduces risk from compromised passwords.

ACCOUNT EXPIRATION

Sets an expiration date for user accounts. Prevents unused or unnecessary accounts from remaining active.

PAM PASSWORD POLICIES

Pluggable Authentication Modules (PAM) enforce password strength, complexity, and reuse rules. Configured in /etc/pam.d/ and /etc/security/.

FAILED AUTHENTICATION ATTEMPTS

Limit and monitor failed login attempts. Helps prevent brute-force and password guessing attacks.

DORMANT ACCOUNTS

Accounts that have not been used for a long time increase risk. Identify and disable or remove dormant accounts.

LOGIN RESTRICTIONS

Restrict login access by time, source IP, or TTY. Enhances security for privileged and system accounts.

REVIEWING PASSWORD STATUS

Regularly review password aging, expiration, and account status. Use tools to ensure policies are enforced.

SECURE SERVICE-ACCOUNT PRACTICES

Use strong, long passwords or keys for service accounts. Restrict permissions and avoid interactive logins.

Service accounts: use long random keys, no interactive shell.

4. FILE AND DIRECTORY
PERMISSIONS

OWNER, GROUP, AND OTHER PERMISSIONS

Every file and directory has three types of access: Owner (user), Group, and Other (everyone else). Permissions control what each can do.

READ, WRITE, AND EXECUTE

R (read): view file contents or list directory. W (write): modify file or create/delete in directory. X (execute): run file or access directory.

NUMERIC AND SYMBOLIC PERMISSIONS

Numeric: use numbers (0-7) to represent permissions. Symbolic: use letters (r, w, x) to set permissions. Example: 755 = rwxr-xr-x.

CHMOD, CHOWN, CHGRP

chmod: change file or directory permissions. chown: change file or directory owner. chgrp: change file or directory group.

DIRECTORY PERMISSION BEHAVIOR

Read (r): list files in the directory. Write (w): create, delete, or rename files. Execute (x): enter and access the directory. Without x, you cannot access files inside.

UMASK

The umask sets default permissions for new files and directories. It determines what permissions are removed by default. Check with: umask.

FINDING DANGEROUS PERMISSIONS

Look for world-writable files and directories. Use tools to find risky permissions. Example: chmod 777 or writable system files.

PRODUCTION PERMISSION MISTAKES

Using 777 permissions; making sensitive files world-readable; incorrect ownership of application files; writable system directories; ignoring umask settings.

PERMISSION REFERENCE
FILE: script.sh
-rw-r--r-- (644)
FILE: application.log
-rw-rw---- (660)
DIR: /var/www
drwxr-xr-x (755)
DIR: /data
drwx------ (700)

Wrong permissions on config files lead to credential leaks. Always audit before deploy.

QUICK CHECK COMMANDS
>_ ls · stat · find
ls -l List files with permissions
namei -l /path/to/file Show full path permissions
stat file.txt Detailed file information
find / -type f -perm -o+w Find world-writable files
find / -type d -perm -002 Find world-writable directories

5. SUID, SGID, STICKY
BIT, AND ACLs

SUID EXECUTABLES

When a file has the SUID bit set, it runs with the permissions of the file owner (usually root). Risk: can be abused to gain elevated privileges. Check SUID files regularly.

SGID FILES AND DIRECTORIES

SGID on files: runs with the group owner's privileges. SGID on directories: new files inherit the directory's group ownership. Helps in controlled group collaboration.

STICKY BIT

On directories, only the file owner, directory owner, or root can delete or rename files. Common on /tmp to prevent users from deleting each other's files.

ACCESS CONTROL LISTS (ACLs)

Provide fine-grained permissions beyond the traditional user/group/other model. Useful for granting access to specific users without changing ownership.

GETFACL AND SETFACL

getfacl: view ACLs on files and directories. setfacl: modify ACLs for fine-grained access. ACLs override standard permissions.

SEARCHING FOR SUID AND SGID BINARIES

Regularly search for SUID/SGID files to detect unexpected privilege escalation paths. New or unknown files can be a security risk.

UNEXPECTED PRIVILEGE PATHS

Attackers exploit misconfigured SUID/SGID files or writable paths to escalate privileges. Always verify owner, permissions, and purpose.

AUDITING SPECIAL PERMISSIONS

Maintain an inventory of all special permission files. Review regularly and document approved exceptions. Remove unnecessary permissions immediately.

SPECIAL PERMISSION TYPES

SUID (4xxx) — run as file owner.

SGID (2xxx) — run as group owner.

STICKY (1xxx) — restricted deletion in directories.

ACLs — extended permissions for specific users/groups.

FIND & ACL COMMANDS
>_ find · getfacl · setfacl
find / -type f -perm -4000 -exec ls -l {} \; Find all SUID files
find / -type f -perm -2000 -exec ls -l {} \; Find all SGID files
find /bin /sbin /usr/bin /usr/sbin -perm -4000 -o -perm -2000 -ls Find SUID/SGID in common paths
getfacl /path/to/file View ACLs
setfacl -m u:user:rw /path/to/file Add ACL entry
setfacl -x u:user /path/to/file Remove ACL entry
setfacl -b /path/to/file Remove all ACLs
AUDIT CHECKLIST

Review all SUID, SGID, and Sticky files.

Verify file purpose and ownership.

Ensure directories with SGID are required.

Check ACLs for unnecessary access.

Document approved exceptions.

Remove or fix unnecessary entries.

6. SUDO AND PRIVILEGE
ESCALATION SECURITY

ROOT ACCESS RISKS

Root has unlimited power on the system. A single mistake or compromise can lead to full system takeover. Limit and monitor root access carefully.

/ETC/SUDOERS

Main sudo configuration file. Controls which users or groups can run which commands as root or another user. Always edit with visudo, never a text editor.

/ETC/SUDOERS.D/

Directory for additional sudo configuration files. Used to add custom rules without modifying the main sudoers file. Each file is included automatically.

VISUDO

Safe way to edit sudoers files. Syntax is checked before saving. Prevents locking yourself out of sudo access. Always use: visudo or visudo -f <file>.

COMMAND-SPECIFIC SUDO ACCESS

Grant users access to only the commands they need. Example: allow restart of specific services without full root access. Reduces the attack surface.

DANGEROUS SUDO CONFIGURATIONS

Avoid broad permissions and wildcard commands. Dangerous: ALL=(ALL) ALL, ALL=(ALL) NOPASSWD: ALL, command wildcards like /bin/*. These can lead to full privilege escalation.

NOPASSWD RISKS

NOPASSWD allows running commands without entering a password. If misconfigured, attackers can escalate privileges without any authentication. Use only when absolutely necessary.

REVIEWING SUDO PRIVILEGES

Regularly review who has sudo access and what they can run. Remove unused or excessive privileges. Use audit logs to monitor sudo activity.

LEAST-PRIVILEGE ADMINISTRATION

Grant only the minimum access required. Remove elevated access when not needed. Use groups, command restrictions, and logging to enforce least-privilege principles.

SUDO COMMAND EXAMPLES
>_ sudo · visudo
sudo -l List allowed sudo commands for current user
sudo -ll List all privileges in detail
sudo -u <user> <command> Run command as another user
visudo Edit /etc/sudoers safely
visudo -f /etc/sudoers.d/<file> Edit a file in sudoers.d directory
sudo -k Invalidate password timestamp
sudo -v Refresh the sudo timestamp
SUDO SECURITY CHECKLIST

Limit users with sudo access.

Use command-specific permissions.

Avoid NOPASSWD unless required.

Do not use wildcards carelessly.

Review /etc/sudoers regularly.

Audit sudo usage in logs.

Remove unnecessary privileges.

Use least-privilege principles.

Test configurations before deployment.

7. SSH SERVER
HARDENING

SSH ATTACK SURFACE

SSH is a common target for attackers. Reduce exposure by limiting access, strengthening authentication, and monitoring activity.

KEY-BASED AUTHENTICATION

Use SSH keys instead of passwords. Stronger, more secure, and resistant to brute-force attacks.

DISABLING ROOT SSH LOGIN

Do not allow root to login via SSH. Use a regular user and sudo for administrative tasks.

DISABLING PASSWORD AUTHENTICATION

Disable password-based login. Prevents brute-force and credential stuffing attacks.

SSHD_CONFIG

Main SSH server configuration file. Harden settings in /etc/ssh/sshd_config and reload SSH service safely.

RESTRICTING USERS AND GROUPS

Allow only specific users or groups to access SSH. Deny all others.

SSH KEY PERMISSIONS

Private key (id_rsa): 600. Public key (id_rsa.pub): 644. ~/.ssh directory: 700. authorized_keys file: 600. Wrong permissions = login failure.

IDLE-SESSION CONTROLS

Set timeouts for idle sessions. Disconnect inactive sessions automatically to reduce risk.

TESTING CONFIGURATION BEFORE RESTART

Always validate SSH configuration before restarting to avoid lockout. Use test mode: sshd -t.

REVIEWING SSH AUTHENTICATION LOGS

Monitor SSH login attempts, failed logins, and suspicious activity regularly. Logs help detect brute-force attacks early.

SSHD_CONFIG — HARDENED BASELINE

8. LINUX SERVICES AND
SYSTEMD SECURITY

IDENTIFYING UNNECESSARY SERVICES

Many services start automatically by default. Remove or disable services you do not need. Every unnecessary service increases your attack surface.

SYSTEMCTL

The primary tool for managing systemd services. Used to start, stop, enable, disable, and inspect services.

ENABLED VERSUS RUNNING SERVICES

Enabled: starts automatically at boot. Running: currently active in memory. A service can be enabled, running, both, or neither.

DISABLING UNUSED SERVICES

Disable services to prevent them from starting at boot. Stop services that are not needed now. Example: systemctl disable --now <service>.

SERVICE USERS

Services should run as an unprivileged user. Avoid running services as root. Check the User= and Group= settings in unit files.

SYSTEMD UNIT PERMISSIONS

Unit files control how services run. Protect unit files from unauthorized changes. Typical path: /etc/systemd/system/. Use proper file permissions.

SERVICE ISOLATION

Use systemd sandboxing to limit damage. Options: ProtectSystem, ProtectHome, PrivateTmp, NoNewPrivileges, RestrictAddressFamilies, and more. Stronger isolation = better security.

RESTART POLICIES

Configure how services behave when they fail. Common policies: no, on-failure, on-abnormal, on-watchdog, always. Use RestartSec= to set delay between restarts.

INSPECTING FAILED OR SUSPICIOUS SERVICES

Check failed services and view recent logs. Look for crash loops, repeated failures, or unexpected behavior. Use systemctl status <service> and journalctl -u <service>.

REDUCING SERVICE ATTACK SURFACE

Run only what you need. Disable, mask, or remove unneeded services. Keep services updated and properly configured. Minimize privileges and isolate workloads.

COMMON SYSTEMCTL COMMANDS
>_ systemctl · journalctl
systemctl list-units --type=service List all services
systemctl list-unit-files --type=service Show enabled/disabled services
systemctl status <service> Show service status and logs
systemctl start <service> Start a service
systemctl stop <service> Stop a service
systemctl restart <service> Restart a service
systemctl enable <service> Enable at boot
systemctl disable <service> Disable from boot
systemctl mask <service> Prevent service from starting
systemctl unmask <service> Unmask a service
systemctl cat <service> Show full unit file
systemctl show <service> Show all properties
BEST PRACTICES

Disable services you do not use.

Run services as non-root users.

Harden services with isolation options.

Limit network and filesystem access.

Monitor service logs and failures.

Keep services updated.

Review services regularly.

Follow least-privilege principles.

ENABLED VS RUNNING
>_ list-unit-files · list-units
systemctl list-unit-files --type=service --state=enabled List enabled services
systemctl list-units --type=service --state=running List running services

9. NETWORK EXPOSURE
AND OPEN PORTS

LISTENING SOCKETS

Listening sockets are endpoints that accept incoming connections or packets on the system.

TCP AND UDP EXPOSURE

Open TCP ports establish connections. Open UDP ports receive datagrams. Both increase the attack surface.

SS

ss is the modern tool to view socket statistics, listening ports, and network connections. Use it to identify what is listening on the system.

LSOF

lsof lists open files and the processes that opened them, including network sockets. Useful for identifying listening ports and connections.

IDENTIFYING PROCESSES BEHIND PORTS

Find which process is listening on a specific port. Understand the service, user, and risk associated with that process.

LOOPBACK VERSUS PUBLIC INTERFACES

Services bound to 127.0.0.1 are only accessible locally. Services bound to 0.0.0.0 or public IPs are accessible from the network or internet.

UNEXPECTED LISTENING SERVICES

Unexpected or unnecessary services listening on ports may indicate misconfiguration or potential compromise. Always review and minimize exposed services.

NETWORK EXPOSURE INVESTIGATION

Investigate open ports, services, and connections. Correlate with logs and configurations to assess the security impact.

PRODUCTION PORT AUDITING

Regularly audit open ports and listening services.

Validate that only required services are exposed.

Document, monitor, and review continuously.

Compare enabled vs running services.

Investigate any unexpected listener immediately.

10. LINUX FIREWALL
SECURITY

HOST-BASED FIREWALL PURPOSE

A host-based firewall controls network traffic to and from your Linux system. It blocks unauthorized access, reduces attack surface, and enforces security policies at the host level.

NFTABLES

nftables is the modern Linux packet filtering framework. It is powerful, fast, and replaces legacy iptables. It supports complex rules, sets, maps, and stateful filtering.

IPTABLES CONCEPTS

iptables is the legacy firewall tool based on tables, chains, and rules. Key tables: filter, nat, mangle, raw. Key chains: INPUT, OUTPUT, FORWARD.

UFW AND FIREWALLD

UFW is a simple frontend for iptables/nftables. firewalld provides a dynamic firewall with zones, services, and runtime management.

DEFAULT-DENY STRATEGY

Start with default deny for incoming connections. Allow only what is required. This minimizes risk by blocking everything except explicitly allowed traffic.

INBOUND VERSUS OUTBOUND RULES

Inbound rules control traffic coming into the system. Outbound rules control traffic leaving the system. Both should be defined intentionally.

RESTRICTING ADMINISTRATIVE PORTS

Limit access to administrative ports (SSH, RDP, etc.) to trusted IPs or networks only. Never expose admin ports to the public internet.

RULE ORDERING

Firewall rules are processed in order from top to bottom. Place specific allow rules before general deny rules. Incorrect ordering can create security gaps.

PERSISTENT FIREWALL CONFIGURATION

Firewall rules must survive reboots. Use appropriate tools to save rules: nft list ruleset > file, iptables-save, ufw enable, firewalld --permanent.

TESTING RULES WITHOUT LOCKING YOURSELF OUT

Always test firewall changes carefully. Use a second SSH session or console access. Apply changes gradually and verify before closing your session.

FIREWALL COMMANDS
>_ nft · iptables · ufw · firewall-cmd
nft list ruleset Show current nftables ruleset
nft add rule inet filter input tcp dport 22 accept Allow SSH in nftables
iptables -L -n -v List iptables rules with counters
iptables -A INPUT -p tcp --dport 22 -j ACCEPT Allow SSH in iptables
iptables-save > /etc/iptables/rules.v4 Save iptables rules
ufw enable Enable UFW
ufw allow 22/tcp Allow SSH in UFW
ufw status verbose Show UFW status
firewall-cmd --permanent --add-service=ssh Add SSH service in firewalld
firewall-cmd --reload Reload firewalld rules
FIREWALL BEST PRACTICES

Default-deny inbound; explicitly allow what is required.

Restrict admin ports to trusted IPs only.

Order specific allows before general denies.

Persist rules across reboots (iptables-save / ufw enable).

Test from a second session before disconnecting.

11. PROCESS AND
RUNTIME SECURITY

PROCESS OWNERSHIP

Every process runs as a specific user and group. Review process ownership to ensure least privilege and detect suspicious activity.

PARENT AND CHILD PROCESSES

Processes are created by other processes. Understanding parent-child relationships helps trace the origin of a process.

PRIVILEGED PROCESSES

Processes running as root or with elevated capabilities pose higher risk. Review and restrict privileged processes.

PS, TOP, PSTREE

Use ps to view processes, top for live monitoring, and pstree to visualize process trees. Essential tools for runtime visibility.

/PROC

The /proc filesystem provides real-time information about processes, memory, mounts, network, and more. Powerful for investigation.

SUSPICIOUS COMMAND LINES

Review process command lines. Look for obfuscated, encoded, or unusual commands that may indicate malicious activity.

UNEXPECTED BINARIES

Processes running from unusual locations (e.g., /tmp, /dev/shm) or unknown binaries may indicate compromise.

LONG-RUNNING PROCESSES

Processes running longer than expected can indicate stuck services or persistence mechanisms. Review and validate regularly.

PROCESSES LISTENING ON THE NETWORK

Identify processes that have open sockets. Ensure only required services are listening on expected ports and interfaces.

INVESTIGATING ABNORMAL RUNTIME ACTIVITY

Correlate process behavior, network activity, and logs to detect anomalies. Investigate immediately and contain threats.

RUNTIME INSPECTION
>_ ps · top · pstree · /proc
ps aux List all processes with user and command
ps -ef --forest Show process tree
top Live process monitor (CPU, memory)
pstree -p Tree view with PIDs
cat /proc/<pid>/cmdline Inspect process command line
cat /proc/<pid>/environ Inspect process environment
ls -l /proc/<pid>/exe Resolve binary path for a process
ss -tulpen Find processes listening on ports

Processes from /tmp, /dev/shm, or /var/tmp.

Obfuscated / base64-encoded command lines.

Long-running unknown binaries.

Process running as root that should not be.

Unexpected outbound network connections.

Deleted-but-running binaries (ls -l /proc/*/exe).

12. LOGGING AND
SECURITY INVESTIGATION

LINUX AUTHENTICATION LOGS

Authentication logs record user logins, logouts, and security-relevant events. Key sources: /var/log/auth.log, /var/log/secure.

JOURNALCTL

journalctl is the systemd log manager. View system, service, kernel, and boot logs. Powerful filtering with time, unit, priority, and more.

/VAR/LOG

Traditional log files stored in /var/log. Contains authentication, system, application, and service logs.

SSH LOGIN EVENTS

Track successful and failed SSH logins. Logs show IP address, user, time, and authentication method. Helps detect brute-force and suspicious access.

SUDO ACTIVITY

Monitor sudo command usage and privilege escalation. Logs show who ran what command and when. Essential for auditing privileged access.

FAILED AUTHENTICATION

Failed login attempts indicate attacks or misconfiguration. Track repeated failures from the same IP or user. Helps identify brute-force and password attacks.

SERVICE FAILURES

Service errors can impact availability and security. Logs show crashes, dependency issues, and start failures. Helps detect misconfigurations and potential attacks.

KERNEL MESSAGES

Kernel logs report hardware, driver, and system events. Important for detecting panics, OOM kills, and security issues. Access via dmesg or journalctl -k.

SEARCHING AND FILTERING LOGS

Use tools like grep, awk, sed, and journalctl filters. Filter by time, user, IP, service, priority, or keywords. Effective searching speeds up investigation.

BUILDING AN INCIDENT TIMELINE

Correlate events from multiple logs to understand what happened. Establish sequence: initial access, actions, and impact. A clear timeline is critical for response and reporting.

LOG INSPECTION COMMANDS
>_ journalctl · grep · last
journalctl -u ssh --since "1 hour ago" SSH logs from last hour

journalctl -k Kernel messages

INVESTIGATION CHECKLIST

Identify time window and time zone of incident.

Pull auth.log + journalctl for that window.

Track failed logins and successful logins.

Trace sudo / su privilege escalation.

Correlate with service + kernel logs.

Build a timeline: initial access, actions, impact.

13. LINUX AUDITING
WITH AUDITD

LINUX AUDIT FRAMEWORK

The Linux Audit Framework provides a comprehensive system for monitoring, recording, and reviewing security-relevant events. It operates at the kernel level for high integrity and reliability.

AUDITD

auditd is the user-space service that collects audit events from the kernel and writes them to the audit log. It is highly configurable and essential for security monitoring.

AUDIT RULES

Audit rules define what events to monitor. Rules can be file watches, syscalls, users, commands, or system calls. Use auditctl to load and manage rules.

WATCHING SENSITIVE FILES

Monitor critical files and directories for reads, writes, attribute changes, and deletions. Example: /etc/passwd, /etc/shadow, /etc/sudoers.

MONITORING PRIVILEGED COMMANDS

Track the use of privileged commands such as sudo, su, useradd, chmod, chown, setuid, and more. Helps detect privilege escalation and misuse.

AUSEARCH

ausearch is used to search the audit log. Filter by time, user, event type, file, PID, or command. Essential for incident investigations.

AUREPORT

aureport generates summarized reports from audit logs. Use it for quick insights on logins, commands, files, and SELinux events.

TRACKING CONFIGURATION CHANGES

Monitor changes to critical configuration files. Detect unauthorized modifications to system settings, services, and security policies.

AUDIT-LOG PROTECTION

Protect audit logs from tampering. Set proper permissions, enable log rotation, and forward logs to a secure, centralized location.

AUDITD COMMANDS
>_ auditctl · ausearch · aureport
auditctl -w /etc/passwd -p wa -k identity Watch /etc/passwd for writes/attr changes
auditctl -w /etc/shadow -p wa -k identity Watch /etc/shadow
auditctl -w /etc/sudoers -p wa -k sudoers Watch /etc/sudoers
auditctl -a always,exit -F path=/usr/bin/sudo -F perm=x -k priv_cmd Audit sudo executions
auditctl -l List current audit rules
auditctl -D Delete all audit rules
ausearch -k identity Search by key
ausearch -m USER_CMD -ts today Today's user commands
aureport --summary Summarized audit report
aureport -x Executable report
PRACTICAL INVESTIGATION EXAMPLES

Detect unauthorized access to /etc/shadow.

Track changes to /etc/sudoers.

Identify privilege escalation via sudo/su.

Watch for unexpected file deletions.

Investigate suspicious activity step-by-step.

14. SELINUX
AND APPARMOR

MANDATORY ACCESS CONTROL

SELinux and AppArmor are Mandatory Access Control (MAC) systems that restrict what processes can do, even if they are compromised or running as root.

SELINUX MODES

SELinux operates in three main modes that determine how policies are enforced: Enforcing, Permissive, and Disabled.

ENFORCING, PERMISSIVE, AND DISABLED

Enforcing: policies are active and violations are blocked. Permissive: policies are active but violations are only logged. Disabled: SELinux is turned off (not recommended).

SELINUX CONTEXTS

SELinux uses security contexts (labels) to define what users, roles, types, and levels a process or file has. Contexts control access decisions.

POLICY VIOLATIONS

When a process is blocked by SELinux, an AVC (Access Vector Cache) denial is logged. These logs show what was blocked and why.

GETENFORCE

getenforce shows the current SELinux mode. Command: getenforce. Example output: Enforcing | Permissive | Disabled.

SESTATUS

sestatus displays SELinux status, mode, policy type, and other important details. Command: sestatus.

APPARMOR PROFILES

AppArmor uses profiles to restrict programs. Each profile defines what the program can access. Profiles are stored in /etc/apparmor.d/.

ENFORCE VERSUS COMPLAIN MODE

Enforce: violations are blocked. Complain: violations are logged but not blocked. Use complain mode to test profiles before enforcing.

TROUBLESHOOTING BLOCKED APPLICATIONS SAFELY

Review AVC logs (ausearch -m avc -ts recent). Identify the blocked action and target. Adjust the policy or profile. Use permissive or complain mode during troubleshooting, then return to Enforcing.

FILE HASHES WITH SHA256SUM

Generate SHA256 hashes for files and verify them against known good values. Used to detect tampering and unauthorized modifications.

FILE INTEGRITY MONITORING

Regularly hash critical files. Store hashes securely. Compare hashes to detect changes. Use tools like AIDE, Tripwire, or OSSEC.

CRON PERSISTENCE

Attackers plant malicious jobs in crontab, /etc/cron.*, or /var/spool/cron/. Check crontab -l and ls -la /etc/cron.* regularly.

SYSTEMD PERSISTENCE

Malicious or unknown systemd services can survive reboots. Inspect systemctl list-unit-files and /etc/systemd/system/ for suspicious units.

SHELL STARTUP FILES

Detect unauthorized changes in ~/.bashrc, ~/.bash_profile, and /etc/profile.d/. Attackers inject commands here to persist across sessions.

SUSPICIOUS BINARIES

Unknown binaries in /tmp, /dev/shm, or user home directories may indicate compromise. Hash, identify, and investigate them.

DETECTING UNAUTHORIZED CHANGES

Monitor critical files and directories. Track new or modified binaries. Review file ownership and permissions. Alert on unexpected changes.

17. SECRETS, CREDENTIALS,
AND SENSITIVE DATA

1. CONFIGURATION FILES

Avoid storing passwords, API keys, or tokens in plain-text config files. Common files: /etc/*.conf, ~/.config/*, /var/www/html/*.php, .env, settings.json.

2. ENVIRONMENT VARIABLES

Environment variables may contain secrets. Check: env, printenv, cat /proc/*/environ. Never pass secrets via env on shared systems.

3. SSH PRIVATE KEYS

Protect private keys at all times. Default location: ~/.ssh/. Check: ~/.ssh/id_rsa. Store securely. Key permissions 600. Avoid hardcoding. Rotate regularly. Never share private keys.

4. DATABASE CREDENTIALS

Credentials should never be stored in plain text. Check config files, scripts, and environment variables. Use vaults or secret managers.

5. FILE PERMISSION MISTAKES

Incorrect permissions can expose secrets. Sensitive files should be readable by owner only. Check: ls -l <file>. Fix with: chmod 600 <file>.

6. SHELL HISTORY EXPOSURE

Commands containing secrets may be saved in history. Check ~/.bash_history. Clear history when needed: history -c && history -w.

7. PROCESS ARGUMENT EXPOSURE

Secrets passed as arguments can be visible to other users. Check running processes: ps aux. Avoid passing secrets as command-line arguments.

8. PROCESS ENVIRONMENT EXPOSURE

Process environ may contain secrets. Check /proc/<pid>/environ. Run secrets-bearing services as isolated users.

9. SECRET ROTATION

Rotate credentials regularly. Revoke old keys and tokens. Automate rotation where possible. Document rotation procedures. Monitor for unused credentials.

10. SEARCHING SYSTEMS FOR EXPOSED CREDENTIALS

Search for common patterns: grep -rni "password|passwd|api_key|secret|token" /. Use tools: ripgrep (rg), trufflehog, git-secrets, gitleaks.

Use a vault or secret manager (no plain text).

Never pass secrets as command-line arguments.

Clear shell history after using secrets.

Scan repositories before every push.
