1. What is Shell Scripting?

The Command-Line Foundations Every DevOps Engineer Needs
Shell vs Terminal vs Bash

Terminal

The application window that lets you type commands and see output. It's the UI, not the brain.

Shell

The interpreter that parses your commands and asks the kernel to run them (bash, zsh, sh, fish…).

Bash

One specific shell (Bourne-Again SHell). Default on most Linux distros & the one this handbook uses.

Why DevOps Engineers Automate with Scripts
Eliminate repetitive toil — run one command, not fifty.
Make deployments repeatable, auditable & reversible.
Codify institutional knowledge instead of sticky-notes.
Reduce human error in fragile production changes.
Enable CI/CD pipelines to run unattended at 3 AM.
Ship a self-contained script instead of a 12-step runbook.
Version control your operations the same way you version code.
Your First Bash Script
hello.sh
#!/bin/bash
$ echo "Hello, DevOps!"
Hello, DevOps!
# Shebang tells the system which shell to use
# Comments start with # and are ignored at runtime
$ name="Alice"
$ echo "Hi, $name"
Hi, Alice
Important Note
Scripts are plain text files. Save with a .sh extension (convention only), mark them executable with chmod +x, then run them with ./script.sh or bash script.sh. No compilation needed.
What a Shell Actually Does
1
Reads your command from stdin (the keyboard).
2

3
Expands variables, globs, and command substitutions.
4
Resolves the command path via $PATH.
5
Asks the kernel to spawn the process.
6
Streams stdout/stderr back to your terminal.

3. Creating & Running Shell Scripts

Turn Commands Into Automation
Creating .sh Files

Use your editor to create a script file with a descriptive name and the .sh extension.

create script
$ nano deploy.sh
$ touch backup.sh
$ chmod +x backup.sh
The Shebang

Line 1 of every script must declare the interpreter so the kernel knows what to run.

shebang
#!/bin/bash
#!/usr/bin/env bash ← portable
#!/bin/sh ← minimal POSIX
# Without it: system may use the wrong shell
Make It Executable

By default new files are not runnable. Grant execute permission, then run directly.

chmod +x
$ chmod +x deploy.sh
$ ./deploy.sh
→ Building...
→ Deploying to prod
Run Your Script

Two equivalent ways to invoke a script:

run script
# Method 1: direct (needs +x & shebang)
$ ./deploy.sh
# Method 2: pass to bash explicitly
$ bash deploy.sh
Tip: Method 2 works even without +x — handy for one-off scripts.

Common Errors
E1
Permission denied — forgot chmod +x.
E2
Command not found — typo or missing $PATH.
E3
bad interpreter — wrong shebang path.
E4
Syntax error near token — unmatched quote or missing fi/done.
Fix: Always run bash -n script.sh to syntax-check before executing.
Debugging Like a Pro
ProblemWhyHow to Fix
Permission denied
 File lacks execute bit. chmod +x script.sh
Script not found
 Wrong path or ./ omitted. ./script.sh (note the dot-slash)
bad interpreter
 Bad shebang or hidden CRLF line endings. dos2unix script.sh then re-check shebang
Syntax error
 Unmatched quote / missing keyword. bash -n script.sh to find the line
Logic wrong, no error
 Variables expanding unexpectedly. bash -x script.sh to trace each step
Best Practices
Always start with #!/bin/bash
Use set -euo pipefail to fail loudly.
Quote every variable: "$VAR"
Comment the why, not the what.
Test with bash -n before running.
Keep scripts under 200 lines; refactor more.
Use shellcheck as your linter.
Exit with explicit codes: exit 1
Remember: A script that fails silently is worse than no script at all. Make noise!

deploy.sh
#!/bin/bash
# A reusable deploy script
$ set -euo pipefail
$ ENV="${1:-staging}"
$ echo "Deploying to $ENV…"
$ ./build && ./test && ./ship "$ENV"
$ echo "Done. ($?)"

→ ship OK

4

6. EXIT CODES & COMMAND SUCCESS

EVERY COMMAND RETURNS A STATUS.
1What Exit Codes Mean

After any command runs, the system returns a number called an exit code. It tells you if the command succeeded or failed.

echo $? — shows the exit code of the last command.

2Basic Exit Code Rules
CodeTypeMeaning
0SuccessCommand completed successfully.
1+Non-zeroFailure — check the error.
3Examples

See exit codes in action.

examples.sh
$ ls /home; echo $? 0 $ ls /nope; echo $? 2 $ cat file.txt; echo $? 0 or 1+
4The exit Command

End a script and return a code.

exit-cmd.sh
if [ ! -f file.txt ]; then echo "File not found!" exit 1 fi # exit 0 = success # exit 1 = failure
5Testing Command Success

Use exit codes in conditions.

test.sh
ls /home if [ $? -eq 0 ]; then echo "Success" else echo "Failed" fi
6Why CI/CD Pipelines Depend on Exit Codes
  • Each step returns an exit code.
  • CI/CD tools stop the pipeline on failure.
  • Exit 0 = pipeline continues.
  • Exit 1+ = pipeline fails.
  • Ensures reliable, consistent deployments.
7Preventing Silent Automation Failures

Validate

Check files & inputs before running.

Log

Capture stdout & stderr for diagnosis.

Document

Track each step in a script log file.

Alert

Surface non-zero exit codes immediately.

Tune

Set set -e for fail-fast behavior.

TipAlways check $? after risky commands
Patternset -e + set -o pipefail

8. LOGICAL OPERATORS

COMBINE COMMANDS. CONTROL FLOW.
1Logical Operators
OperatorMeaningExample
&&AND — run next if previous succeedscmd1 && cmd2
||OR — run next if previous failscmd1 || cmd2
!NOT — invert exit status! cmd
2Short-Circuit Execution
&&
AND — runs the second command only if the first succeeds (exit 0).
||
OR — runs the second command only if the first fails (non-zero).
!
NOT — inverts the exit status of a command.
Efficiency — shell skips commands that cannot change the result.
3AND Conditions

Run a chain only if every step succeeds.

and.sh
mkdir build && cd build && make # only proceeds if each step returns 0
OKAll three commands ran successfully.
4OR Conditions

Provide a fallback when the first command fails.

or.sh
cat config.cfg || echo "missing config" # prints fallback if cat fails
OKReads file or reports missing.
5NOT Condition

Invert a test result (useful in if blocks).

not.sh
if [ ! -f /tmp/lock ]; then echo "lock absent — proceed" fi
OKProceeds only when lock is absent.
6Combining Multiple Tests

Stack operators for richer logic. Examples 1, 2, and 3 below.

Example 1 — File exists & readable
ex1.sh
if [ -f app.conf ] && [ -r app.conf ]; then echo "config OK" fi
Example 2 — Ping or fallback
ex2.sh
ping -c1 host || echo "down"
Example 3 — Both required
ex3.sh
[ -d logs ] && [ -w logs ] || exit 1
Safe Deployment
  • Verify preconditions.
  • Capture every failure.
  • Provide meaningful fallbacks.
  • Use set -e for safety.
Safe DeploymentAlways validate inputs and exit codes before acting on results.
7Building Safer Checks

Combine operators with explicit tests for robust scripts.

safe.sh
#!/bin/bash set -e [ -f /etc/app.conf ] && source /etc/app.conf || exit 1 [ -n "$APP_KEY" ] || { echo "missing APP_KEY"; exit 2; } deploy "$APP_KEY"

9. LOOPS FOR AUTOMATION

REPEAT TASKS. SAVE TIME. ELIMINATE MANUAL WORK.
1For Loops

Iterate over a list or range.

for.sh
for i in 1 2 3; do echo "Item $i" done
2While Loops

Repeat while a condition is true.

while.sh
n=0 while [ $n -lt 3 ]; do echo "n=$n" n=$((n+1)) done
3Looping Through Files

Process every file in a directory.

files.sh
for f in /etc/*.conf; do echo "$f" done
4Looping Through Servers

Run a command on each host.

hosts.sh
for h in web1 web2 web3; do ssh $h "uptime" done
5Break

Exit the loop early when a condition is met.

break.sh
for i in 1 2 3 4 5; do if [ $i -eq 3 ]; then break; fi echo "$i" done 1 2
6Continue

Skip the current iteration and continue with the next.

continue.sh
for i in 1 2 3 4 5; do if [ $((i%2)) -eq 0 ]; then continue; fi echo "$i" done 1 3 5
7Avoiding Infinite Loops
  • Always increment or decrement the counter.
  • Use break for an explicit exit.
  • Set a maximum iteration cap.
  • Use set -e to abort on errors.
RiskA forgotten counter hangs the script forever.
8Automating Repetitive Tasks
  • Back up logs nightly.
  • Rotate files older than 7 days.
  • Poll a service until ready.
  • Run health checks across hosts.
  • Process CSV rows one by one.
  • Apply config to multiple nodes.
Key TakeawayAutomate, do not repeat

16. ERROR HANDLING & SAFER SCRIPTS

FAIL FAST. VALIDATE. CLEAN UP. STAY PREDICTABLE.

1. WHY SCRIPTS FAIL SILENTLY

By default, bash ignores errors and keeps going — hiding real issues.

Problem: A failed command does not stop the script. The next line runs anyway, often producing wrong results.

2. SET -E: EXIT ON ERROR

Stop the script as soon as any command fails.

bash
set -e\n# script exits if any command returns non-zero
Benefit: Catches the first failure immediately.

3. SET -U: ERROR ON UNSET VARS

Fail when an undefined variable is used.

bash
set -u\necho "$UNDEFINED" # fails fast
Benefit: Catches typos and missing inputs.

4. SET -O PIPEFAIL: CATCH PIPE ERRORS

Detect failures inside pipelines.

bash
set -o pipefail\ncat file.txt | grep "ERROR" | wc -l
Benefit: Without pipefail, only the last command's status is checked.

5. SET -EUO PIPEFAIL: STRONG & SAFE MODE

Best practice — combine all three flags.

bash
set -euo pipefail
  • Exit on any command error
  • Error on unset variables
  • Catch pipeline failures

6. VALIDATING INPUTS

Always verify inputs before using them.

bash
if [ -z "$1" ]; then\n echo "Usage: $0 <url>"\n exit 1\nfi
Benefit: Prevents errors and makes scripts user-friendly.

7. CHECKING DEPENDENCIES

Ensure required commands exist before running.

bash
if ! command -v curl >/dev/null 2>&1; then\n echo "curl not found!"\n exit 1\nfi
Benefit: Avoids failures due to missing tools.

8. HANDLING FAILED COMMANDS

Check command results and handle failures.

bash
if ! rm file.txt; then\n echo "Failed to remove file.txt"\n exit 1\nfi
Benefit: React to failures and prevent bad outcomes.

9. CLEANING UP AFTER FAILURES

Use traps to clean up on exit or error.

bash
cleanup() {{\n echo "Cleaning up..."\n rm -f temp.log\n}}\ntrap cleanup EXIT
Benefit: Keeps systems clean even when scripts fail.

10. WRITING PREDICTABLE AUTOMATION

Follow these rules for reliable scripts:

  • Fail fast
  • Validate inputs
  • Check dependencies
  • Handle errors
  • Clean up properly
  • Log what happens
  • Exit with the right status code

EXAMPLE: SAFE SCRIPT TEMPLATE

A complete template combining all safety flags.

safe.sh
#!/bin/bash\nset -euo pipefail\n\n# Check input\nif [ -z "$1" ]; then\n echo "Usage: $0 <url>"; exit 1\nfi\n\n# Check dependency\ncommand -v curl >/dev/null 2>&1 || {{ echo "curl not found"; exit 1; }}\n\n# Cleanup trap\ncleanup() {{ rm -f temp.log; }}\ntrap cleanup EXIT\n\n# Main logic\nURL="$1"\nHTTP_CODE=$(curl -s -o /dev/null -w "%{{http_code}}" "$URL")\nif [ "$HTTP_CODE" -ge 200 ] && [ "$HTTP_CODE" -lt 400 ]; then\n echo "[$URL] UP (HTTP $HTTP_CODE)"\nelse\n echo "[$URL] DOWN (HTTP $HTTP_CODE)"; exit 1\nfi
WHY SCRIPTS FAIL

Without safety flags, scripts:

  • Ignore command failures
  • Use unset variables as empty
  • Hide pipeline errors
  • Continue after critical issues

17. DEBUGGING SHELL SCRIPTS

FIND ISSUES. UNDERSTAND CAUSES. FIX FAST.

1. READING SHELL ERRORS

Errors tell you what went wrong. Read them carefully — the message always gives a clue.

bash
./script.sh: line 10: mycmd: command not found\n./script.sh: line 15: [ : : integer expression expected\nPermission denied\nNo such file or directory
Tip: The error message always gives a clue. Look at the line number and message.

2. DEBUG MODE WITH BASH -X

Run your script with bash -x to see each command as it executes.

bash
$ bash -x script.sh\n# Example output:\n+ echo "Starting"\nStarting\n+ VAR=hello\n+ echo $VAR\nhello\n+ ls /not/exist\nls: cannot access '/not/exist': No such file or directory

3. DEBUG MODE INSIDE SCRIPT

Use set -x to enable debug inside the script.

bash
set -x\n# Your commands here\nset +x # Turn off debug
Benefit: Shows each command as it runs. Very helpful to trace issues.

4. COMMON PROBLEMS & FIXES

Six common failure categories:

A. SYNTAX ERRORS

Missing symbols or wrong structure.

if [ "${VAR}" = "x" ] echo "missing fi"

Fix: check brackets, then/fi, do/done.

B. QUOTING PROBLEMS

Wrong quotes break the script.

echo "Hi $USER" # ok echo 'Hi $USER' # literal echo "He said "hi"" # bad

Fix: use double quotes; escape inner.

C. MISSING VARIABLES

Using variables that are not set.

echo $NAME ./script.sh: line 5: NAME: unbound variable

Fix: define or use ${NAME:-default}.

D. PERMISSION ERRORS

Script or files not executable.

./script.sh: line 3: ./other.sh: Permission denied

Fix: chmod +x script.sh.

E. PATH PROBLEMS

Command not found.

mycmd: command not found

Fix: check PATH or use full path.

F. FILE MISSING

File or directory does not exist.

cat: file.txt: No such file or directory

Fix: verify path; use absolute path.

5. DEBUGGING STEP BY STEP

A repeatable workflow for fixing any script:

1. Read the error — Understand what the error says. Note the line number and message.
2. Reproduce the issue — Run the script and confirm the error happens again.
3. Run with bash -x — Use bash -x script.sh to see each command and where it fails.
4. Check variables and quotes — Make sure variables are set and quoted correctly.
5. Fix and test again — Make the change and run again. Repeat until the error is gone.
6. Remove debug — Remove set -x or stop using bash -x after fixing.
COMMON ERROR MESSAGES

What each message usually means:

  • command not found — PATH issue or typo.
  • Permission denied — missing +x or wrong owner.
  • No such file — path typo or missing file.
  • unbound variable — used with set -u.
  • integer expression expected — non-numeric in [ ].
  • unexpected token — missing fi, done, or quote.
