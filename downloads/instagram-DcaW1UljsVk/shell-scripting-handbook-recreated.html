1. WHAT IS SHELL SCRIPTING?

SHELL VS TERMINAL VS BASH

TERMINAL: The application you open — a text interface to interact with the computer.
SHELL: The program that interprets your commands and talks to the OS.
BASH: "Bourne Again SHell" — the most common Linux shell; a command language and scripting interpreter.

WHAT A SHELL ACTUALLY DOES

1. Reads your command.
2. Parses (understands) the command.
3. Expands variables, wildcards, paths.
4. Executes the command or program.
5. Returns the output and exit status.
6. Waits for the next command.

User → Shell → Kernel → Output

COMMAND EXECUTION FLOW

You type a command → Shell interprets it → Kernel executes it → Output + Exit status

WHY DEVOPS ENGINEERS AUTOMATE WITH SCRIPTS

  • Save time and reduce manual work.
  • Eliminate human errors.
  • Ensure repeatability and consistency.
  • Scale operations easily.
  • Automate deployments, monitoring, backups, and more.
  • Integrate with CI/CD pipelines.
  • Improve reliability and speed.

YOUR FIRST BASH SCRIPT

1 #!/bin/bash → Shebang: tells the system to use Bash
2 # This is my first script → Comment: ignored by the shell
3 echo "Hello, DevOps Engineer!" → Prints a message to the screen
4 DATE=$(date) → Stores the current date in a variable
5 echo "Today is: $DATE" → Prints the date
Interactive Commands vs Scripts

Interactive Commands

  • You type and run one command at a time.
  • Used for ad-hoc tasks.
  • Hard to repeat.
  • Not version controlled.
  • Easy to forget commands.

Scripts

  • You write commands in a file and run them.
  • Used for automation.
  • Repeatable and consistent.
  • Version controlled (Git).
  • Easy to share and reuse.
Running a Script Safely
1. CREATE THE FILE
nano myscript.sh
2. SAVE AND EXIT
CTRL + O, ENTER, CTRL + X
3. MAKE IT EXECUTABLE
chmod +x myscript.sh
4. RUN THE SCRIPT
./myscript.sh
5. BEST PRACTICES — Review your script before running · Use full paths for important commands · Test in a safe environment first.
IMPORTANT NOTE: A script has the same power as the user who runs it. Always review scripts before executing, especially scripts from the internet.

6. EXIT CODES AND COMMAND SUCCESS

EVERY COMMAND RETURNS A STATUS.

1. What Exit Codes Mean

After any command runs, the system returns a number called an exit code. It tells you if the command succeeded or failed.

echo $? — Shows the exit code of the last command.

2. Basic Exit Code Rules

Codes follow a simple convention:

CodeTypeMeaning
0SuccessCommand completed successfully.
1+Non-zeroFailure — something went wrong. Check the error.

3. Examples

See exit codes in action for common commands.

examples.sh
$ ls /home; echo $?
0

$ ls /notfoundfolder; echo $?
2

$ cat file.txt; echo $?
0 or 1+

4. The exit Command

Use exit to end a script and return a code. exit 0 = success, exit 1 = failure.

exit-cmd.sh
if [ ! -f file.txt ]; then
  echo "File not found!"
  exit 1
fi

# exit 0 = success
# exit 1 = failure
# Ends the script with a status.

5. Testing Command Success

Use exit codes in conditions. $? -eq 0 = success, $? -ne 0 = failure.

test-success.sh
ls /home
if [ $? -eq 0 ]; then
  echo "Success"
else
  echo "Failed"
fi
6. Why CI/CD Pipelines Depend on Exit Codes
  • ●Each step returns an exit code.
  • ●CI/CD tools stop the pipeline on failure.
  • ●Exit code 0 = pipeline continues.
  • ●Exit code 1+ = pipeline fails.
  • ●Ensures reliable and consistent deployments.
7. Preventing Silent Automation Failures
  • ✓Always check exit codes. Don't ignore command results.
  • ✓Use set -e to exit on error. Stops the script on first failure.
  • ✓Log errors clearly. Makes debugging much easier.
  • ✓Validate inputs before running. Bad inputs cause unexpected failures.
  • ✓Test your scripts regularly. Catches issues early.
TIP: Never ignore exit codes. Check them, handle them, and your scripts will be reliable and safe.

8. LOGICAL OPERATORS AND MULTIPLE CONDITIONS

COMBINE TESTS. MAKE SMARTER DECISIONS.

1. Logical Operators

Combine multiple tests with these three operators:

OpMeaningExample
&&AND — both must be trueif [ $a -gt 5 ] && [ $b -lt 10 ]
||OR — at least one trueif [ $a -gt 5 ] || [ $b -lt 10 ]
!NOT — reverses the resultif ! [ -f file.txt ]

2. Short-Circuit Execution

  • &&If the first condition is false, the second is NOT executed.
  • ||If the first condition is true, the second is NOT executed.
  • !Flips true to false, and false to true.

💡 Saves time and prevents unnecessary checks.

3. AND Conditions ( && )

Both conditions must be true.

and.sh
# Both conditions must be true.
if [ -f app.sh ] && [ -x app.sh ]; then
  echo "File exists and is executable"
else
  echo "Check failed"
fi

✅ Use for strict requirements.

4. OR Conditions ( || )

At least one condition must be true.

or.sh
# At least one condition must be true.
if [ -f app.sh ] || [ -f app.py ]; then
  echo "Script found"
else
  echo "No script found"
fi

✅ Use for alternatives.

5. NOT Condition ( ! )

Reverse a condition.

not.sh
# Reverse a condition.
if [ ! -f config.env ]; then
  echo "Config file missing"
else
  echo "Config file exists"
fi

✅ Use to detect missing items.

6. Combining Multiple Tests

Mix &&, ||, and ! for powerful checks.

combo.sh
# EXAMPLE 1: MIX & OR
if [ -f deploy.sh ] && [ -x deploy.sh ] ||
   [ -f deploy.py ]; then
  echo "Ready to deploy"
else
  echo "Deployment script missing"
fi
✓ Executable deploy.sh OR deploy.py exists.
negation.sh
# EXAMPLE 2: NEGATION WITH AND
if [ ! -f .lock ] && [ -d /var/log ]; then
  echo "Safe to proceed"
else
  echo "Lock file exists or log directory missing"
fi
✓ No lock file AND directory exists.
complex.sh
# EXAMPLE 3: COMPLEX COMBINATION
if [ -f app.conf ] && [ -r app.conf ] &&
   ! [ -z "$1" ]; then
  echo "All checks passed"
else
  echo "Validation failed"
fi
✓ File exists, readable AND first argument is not empty.
7. Safer Deployment Checks

Before deploying, validate everything.

deploy-check.sh
# Before deploying, validate everything.
if [ -f app.tar.gz ] && [ -s app.tar.gz ] && [ -x /usr/bin/docker ] &&
   ! systemctl is-active --quiet app; then
  echo "All checks passed. Starting deployment..."
  # Your deployment commands here
else
  echo "Deployment aborted. Check requirements."
  exit 1
fi
  • ✓ File exists AND not empty
  • ✓ Docker is installed
  • ✓ App service is not running
  • ✓ Proceed only when everything is correct
  • ✓ Prevents failed or risky deployments
TIP: Combine checks, validate early, and fail fast. Smart conditions = reliable automation.

9. LOOPS FOR AUTOMATION

REPEAT TASKS. SAVE TIME. ELIMINATE MANUAL WORK.

1. For Loops

Loop through a list of items.

for.sh
for item in a b c; do
  echo "Item: $item"
done

# Output:
Item: a  Item: b  Item: c

2. While Loops

Repeat while a condition is true.

while.sh
count=1
while [ $count -le 5 ]; do
  echo "Count: $count"
  count=$((count + 1))
done

# Output: Count: 1 2 3 4 5

3. Looping Through Files

Process each file in a directory.

files.sh
for file in *.txt; do
  echo "File: $file"
done

# Prints all .txt files in the current directory.

4. Looping Through Servers

Run commands on multiple servers.

servers.sh
for server in server1 server2 server3; do
  echo "Checking $server..."
  ssh $server uptime
done

# Check uptime on many servers.

5. Break

Exit the loop immediately.

break.sh
for i in {1..5}; do
  if [ $i -eq 3 ]; then
    break
  fi
  echo "Number: $i"
done

# Output: Number: 1 2
# STOP THE LOOP

6. Continue

Skip the rest of the loop and continue.

continue.sh
for i in {1..5}; do
  if [ $i -eq 3 ]; then
    continue
  fi
  echo "Number: $i"
done

# Output: Number: 1 2 4 5
# SKIP AND CONTINUE
7. Avoiding Infinite Loops

Always update your condition. Always change the variable inside the loop. Use clear exit conditions. Test with small values first.

  • ⚠Always change the variable inside the loop.
  • ⚠Use clear exit conditions.
  • ⚠Test your loops with small values first.
  • ⚠Use break when needed.

16. Error Handling and Safer Scripts

WRITE PREDICTABLE. RELIABLE. SAFE AUTOMATION.

1. WHY SCRIPTS FAIL SILENTLY

By default, Bash continues even when commands fail.

bash
rm file.txt echo "Deleted" echo "Script finished"
Problem: If rm fails, the script keeps running and hides the error.

2. SET -E: EXIT ON ERROR

Exit immediately if any command fails.

bash
set -e rm file.txt echo "This runs only if rm succeeds"
Benefit: Stops the script when a command fails.

3. SET -U: ERROR ON UNSET VARIABLES

Exit if you use a variable that is not set.

bash
set -u echo $UNSET_VAR
Benefit: Catches typos and missing variables early.

4. SET -O PIPEFAIL: CATCH PIPE ERRORS

Detect failures inside pipelines.

bash
set -o pipefail cat file.txt | grep "ERROR" | wc -l
Benefit: Without pipefail, only the last command's status is checked.

5. SET -EUO PIPEFAIL: STRONG & SAFE MODE

Best practice for safer scripts.

bash
set -euo pipefail
  • ✔ Exit on any command error
  • ✔ Error on unset variables
  • ✔ Catch pipeline failures

6. VALIDATING INPUTS

Always verify inputs before using them.

bash
if [ -z "$1" ]; then echo "Usage: $0 <url>" exit 1 fi
Benefit: Prevents errors and makes scripts user-friendly.

7. CHECKING DEPENDENCIES

Ensure required commands exist before running.

bash
if ! command -v curl >/dev/null 2>&1; then echo "curl not found!" exit 1 fi
Benefit: Avoids failures due to missing tools.

8. HANDLING FAILED COMMANDS

Check command results and handle failures.

bash
if ! rm file.txt; then echo "Failed to remove file.txt" exit 1 fi
Benefit: React to failures and prevent bad outcomes.

9. CLEANING UP AFTER FAILURES

Use traps to clean up on exit or error.

bash
cleanup() { echo "Cleaning up..." rm -f temp.log } trap cleanup EXIT
Benefit: Keeps systems clean even when scripts fail.

10. WRITING PREDICTABLE AUTOMATION

  • ✔ Fail fast
  • ✔ Validate inputs
  • ✔ Check dependencies
  • ✔ Handle errors
  • ✔ Clean up properly
  • ✔ Log what happens
  • ✔ Exit with the right status code

Result: Reliable and predictable automation every time.

EXAMPLE: SAFE SCRIPT TEMPLATE

bash
#!/bin/bash set -euo pipefail # Check input if [ -z "$1" ]; then echo "Usage: $0 <url>" exit 1 fi # Check dependency command -v curl >/dev/null 2>&1 || { echo "curl not found!"; exit 1; } # Function to cleanup cleanup() { echo "Cleaning up..."; rm -f temp.log; } trap cleanup EXIT # Main logic URL="$1" HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" "$URL") if [ "$HTTP_CODE" -ge 200 ] && [ "$HTTP_CODE" -lt 400 ]; then echo "[$URL] is UP (HTTP $HTTP_CODE)" else echo "[$URL] is DOWN (HTTP $HTTP_CODE)" exit 1 fi

17. Debugging Shell Scripts

FIND ISSUES. UNDERSTAND CAUSES. FIX FAST.

1. READING SHELL ERRORS

Errors tell you what went wrong. Read them carefully.

bash
./script.sh: line 10: mycmd: command not found ./script.sh: line 15: [ : : integer expression expected Permission denied No such file or directory
TIP: The error message always gives a clue.

2. DEBUG MODE WITH bash -x

Run your script with bash -x to see each command.

bash
$ bash -x script.sh
# Example output:
+ echo "Starting" Starting + VAR=hello + echo $VAR hello + ls /not/exist ls: cannot access '/not/exist': No such file or directory

3. DEBUG MODE INSIDE SCRIPT

Use set -x to enable debug inside the script.

bash
set -x # Your commands here set +x # Turn off debug
BENEFIT: Shows each command as it runs. Very helpful to trace issues.

4. COMMON PROBLEMS AND HOW TO FIND THEM

Six common failure categories:

A. SYNTAX ERRORS

Missing symbols or wrong structure.

if [ "${VAR}" = "test" ]
echo "Missing fi"
# Error here

Fix: Check brackets, quotes, then/fi, do/done.

B. QUOTING PROBLEMS

Wrong quotes break the script.

echo "Hello $USER" # Good
echo 'Hello $USER' # Literal
echo "He said "hi"" # Bad

FIX: Use double quotes for variables. Escape inner quotes.

C. MISSING VARIABLES

Using variables that are not set.

echo $NAME
./script.sh: line 5: NAME: unbound variable

Fix: Define the variable or use default: ${NAME:-John}

D. PERMISSION ERRORS

Script or files are not executable.

./script.sh: line 3:
./other.sh: Permission denied

Fix: Use chmod +x script.sh and check file permissions.

E. PATH PROBLEMS

Command not found.

mycmd: command not found

Fix: Check PATH or use full path: /usr/bin/mycmd

F. FILE OR DIRECTORY MISSING

File or directory does not exist.

cat: file.txt: No such file or directory

Fix: Check the path and filename. Use absolute path if needed.

5. DEBUGGING SCRIPTS STEP BY STEP

1
Read the error — Understand what the error is saying. Look at the line number and message.
2
Reproduce the issue — Run the script and confirm the error happens again.
3
Run with bash -x — Use bash -x script.sh to see each command and where it fails.
4
Check variables and quotes — Make sure variables are set and quoted correctly.
5
Fix and test again — Make the change and run again. Repeat until the error is gone.
6
Remove debug — Remove set -x or stop using bash -x after fixing.
KEY TAKEAWAY: Good debugging saves hours. Read errors. Use tools. Fix the root cause.
